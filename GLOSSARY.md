# GLOSSARY

Domain vocabulary for pi-goal. Terms are used exactly as defined here in issue
titles, code, tests, and documentation; if a concept is missing, that is a gap to
close rather than a licence to invent a synonym.

| Term | Definition |
| --- | --- |
| **Goal** | A durable, session-scoped objective with a lifecycle status, a stable identity, and usage accounting. Persisted as custom session entries and reconstructed from the active session branch. One Goal per session at a time. |
| **Goal creation authority** | The short-lived, one-shot authorization to create a Goal from an explicit user or system request in the current request-driven execution. It is corroborated at execution time by a verbatim quotation matched case-sensitively (whitespace-folding only) against the one currently authoritative source: the raw interactive/RPC user input or a Pi custom message. Skill/template expansion, other transformed prompt text, extension-originated `sendUserMessage` input, and standing system-prompt instructions are not evidence. Newer requests replace it, and settlement, session restart, branch navigation, successful creation, and direct Goal lifecycle decisions revoke it. A rejection leaves it valid for a corrected retry; a snapshot gains no quotation, source-message id, or reusable marker. |
| **Objective** | The user's finish line, stored verbatim and never rewritten by the extension. The one part of a Goal message the extension does not author, which is why it is always rendered as delimited, encoded data. |
| **Lifecycle status** | One of `active`, `paused`, `blocked`, `usage_limited`, `budget_limited`, `complete`. Only `active` continues automatically; every other status is a stop. Clearing is a durable tombstone, not a status. |
| **Continuation** | One further provider request pi-goal asks for at `agent_before_settle`, delivered as a `goal-continuation` custom message that restates the objective and asks for an evidence audit. Never scheduled by a timer and never driven from `agent_end`. |
| **Goal turn** | One run of Goal work: the run the user started (the kickoff) plus every run Pi started because pi-goal asked for a continuation. It is a *chain* of runs, because Pi can retry a failed provider request into a second run of the same Goal turn, and can compact for overflow recovery — a recoverable length stop or a context-overflow error — and retry the same response into another. The unit the blocked audit counts, and the unit the anti-loop counters count — although those only count *automatic* Goal turns, because a kickoff or a user-started run is attended. Evaluated at the settlement boundary, the only point where a Goal turn is known to be over. |
| **Activity** | Anything in a Goal turn that could move the objective: a tool call, non-whitespace output, or non-empty reasoning. Its absence is what an activity-free turn means. |
| **Completion audit** | The requirement-by-requirement, current-state-evidence check the model performs before calling `update_goal` with `complete`. Model-executed and extension-enforced only at the lifecycle level. |
| **Blocked audit** | The rule that the same genuine blocker must persist for at least three consecutive Goal turns before a Goal may become `blocked`. Enforced by the extension, not trusted to the model. Consecutiveness, per-turn idempotence, and every reset are the extension's rules too. |
| **Blocker** | The genuine condition preventing progress, as the model reports it through `update_goal`. Its identity — not its wording — decides whether two reports describe the same condition. |
| **Blocker identity** | The opaque identity the extension issues for one blocked-audit chain, published in the structured `update_goal` and `get_goal` payloads and restated by every Continuation while the audit is open. Reusing it verbatim in `blocker_id` marks differently worded reports as the same condition; omitting it reports a genuinely different condition and starts a fresh chain at one; an identity the extension did not issue for the currently open audit is refused without Goal mutation. It is never derived from the blocker text — no normalization, similarity, or hashing is involved — so it neither proves that the condition is genuine nor satisfies the audit by itself. |
| **No-progress check** | The classification of the previous Goal turn as **progress**, a **verified wait**, or **no progress**. A verified wait polls a specific live handle; status narration and unexecuted plans are no progress. |
| **Conservative stop** | A deterministic, extension-owned stop that does not depend on the model's cooperation: repeated activity-free automatic Goal turns, or repeated execution-unavailable automatic Goal turns. Both move the Goal to `blocked`, which `/goal resume` ends with a fresh blocked audit. |
| **Activity-free turn** | An *automatic* Goal turn with no activity at all: no tool call, no output, no reasoning. Three in a row stop the Goal as `blocked`. A kickoff or a user-started run is attended work and never counts. |
| **Execution-unavailable turn** | An *automatic* Goal turn in which the model tried to run a command and the shell itself could not run it. An ordinary command failure — a non-zero exit code, a timeout, or an aborted command — is not one. Only a shell command that actually ran breaks the chain: a successful `get_goal` says nothing about the shell, and a shell call that never ran (invalid arguments, a permission block) is neither an execution failure nor evidence that the shell works, so it cannot hide a spawn failure. A Goal turn that ran no command at all also breaks the chain. Three in a row stop the Goal as `blocked`. |
| **Usage limit** | A provider failure whose evidence says the account, plan, or budget is exhausted. Read in two tiers: account or plan depletion (a provider usage-limit error code, a usage limit, a billing, plan, spending, account, or subscription limit in either word order, an account/plan/period quota or budget, an empty credit pool) is decisive and survives throttle wording in the same failure; a bare quota plus an exhaustion verb is not, because that is also how a per-minute quota metric is described. Moves the Goal to `usage_limited`, which `/goal resume` ends once the limit is resolved. A transient rate limit, an internal budget (`retry budget exhausted`), a negated statement, and a lookup — including a qualified one such as `account quota service reached a timeout`, because what decides is the *head* of the verb's object (its last word), not how the subject or a modifier was worded — are not one. Naming the API or the service as the *scope* of a limit (`You have reached your usage limit for the Anthropic API`, `Monthly usage limit reached for this service`, `You have reached the API usage limit`, `You have reached your service usage limit`) is still a usage limit: the verb reached a limit, not a lookup. The head cuts both ways, so `You have reached the quota service`, `You have reached the account quota service`, `You have reached the billing limit check`, and `You have reached the usage limit service` are lookups: the limit vocabulary in front of them is a modifier, and the object is the service or the check. The head noun is read rather than the raw end of the phrase, so a trailing comma, an exclamation mark, or a trailing adverb cannot hide it (`You have reached the quota service, please retry`, `You have reached the quota service now`), and the phrasal verb `reached out to` reaches what follows its particle. |
| **Terminal provider error** | A provider failure that is not a usage limit and that Pi is not retrying. It stops the continuation for that run and is surfaced, but it leaves the Goal active, so it is a per-run stop rather than a Conservative stop. |
| **User action** | A prompt the user types (including one queued while the agent is busy) or an abort. Ends the unattended phase and resets the anti-loop counters and the blocked audit. |
| **Replacement Goal** | A new Goal identity taking over a session's single Goal slot and starting with zero Goal-owned usage. Work already admitted for the previous identity is never transferred to it and remains attributed to that identity: the old admission segment stays open past the replacement commit until the next freeze boundary (see **Superseded Goal record**), so the old identity's in-flight response and tool results are charged to it and frozen onto its durable superseded record. Clear of the replacement does not close that admission: the superseded segment stays open past the tombstone until the next freeze boundary, so the old identity's in-flight work is still attributed to it. Clear does not rewrite historical ownership, but after its tombstone the current session has no Goal, publishes no further usage for the cleared identity, and never reassigns that work to a future Goal. |
| **Superseded Goal record** | The durable historical snapshot of a Goal identity that has been replaced, marked `superseded` in the session entry. It carries the old identity's accounted usage and status — including budget exhaustion caused by its in-flight tail — and is never rewritten, continued, or transferred to the replacement. A replacement first writes the old identity's already-accounted totals as a durable *current* snapshot (so a crash before the new identity's snapshot still reconstructs the old Goal), then freezes the old identity's in-flight tail onto a superseded snapshot at the next freeze boundary. Because it is marked `superseded`, it never selects the current Goal: the newest *current* snapshot does, so a crash immediately after the freeze still reconstructs the replacement. The freeze boundaries are the delivery of the next user message, a process shutdown that keeps the session file, a new Goal creation, a second replacement, a durability-rollback restore, and the first load of a branch whose freeze boundary never ran; Clear of the replacement keeps an open tail open past the tombstone rather than freezing it, and a tail that collected nothing new is not written at a boundary that carries its own marker on the branch, so an idle replacement does not grow the snapshot log. The two markerless boundaries — creating a new Goal and a second replacement — do write a clean tail, because the freeze is the only entry that tells the replay the admission closed; without it the live path refuses the old identity's late response while the replay still charges it. A durability-rollback restore freezes the tail onto the record it writes and keeps that identity's admission open, so a response still streaming when the replacement was retracted stays with it. |
| **Goal-owned work** | Work explicitly admitted as part of a Goal, beginning at its first work message rather than retroactively at record creation. Attribution lasts through that work's completion even if the Goal's status changes; ordinary prompts and creation controls are excluded. |
| **Admission segment** | The span of work opened by a Goal work message — the `/goal` kickoff, an objective edit, a resume, an automatic Continuation, or the one Budget wrap-up — and closed by a genuine user prompt or a new Goal identity. Only work inside an open segment is charged to that identity. Both ends are decided when Pi *delivers* the message, not when it is queued or typed: a queued steer reaches the branch only after the in-flight response and its tool results, so opening or closing at queue time would move work across the identity or lifecycle boundary that actually owns it. A replacement is the one exception to "a new Goal identity closes it": the old identity's segment stays open past the replacement commit until the next freeze boundary, so its in-flight response and tool results remain attributed to the old identity and are frozen onto its superseded record rather than dropped or charged to the replacement. Clear of the replacement is not a closer either: the superseded segment stays open past the tombstone until the next freeze boundary. A crash inside that window is recovered the same way: the branch is replayed, the tail is rebuilt, and the first load freezes it. A *new* Goal identity — a fresh creation, or a second replacement — does close it, and durably: that boundary leaves no marker of its own on the branch, so the close is written as the superseded snapshot the replay already reads, which is what keeps the live refusal and the replay's attribution identical. A durability-rollback restore is the mirror image: it retracts the replacement, so the restored identity's own segment is open again and the response it was streaming is charged to it, with no new automatic work admitted for it. |
| **Legacy reconstructed totals** | The token and active-time baseline recovered from a pre-repair 0.1.0 Goal under the 0.1.0 status-only accounting rules and then frozen as historical. They are **not** exact Goal-owned attribution rebuilt under the repaired rules, and user-facing documentation must say so. |
| **Cutover** | The one-time, branch-local migration of a pre-repair (0.1.0) snapshot: reconstruct the legacy totals once under 0.1.0 rules, freeze them, and durably write the repaired snapshot plus a `goal-cutover` marker before admitting repaired Goal work. A fork copied before the cutover migrates itself when selected; a fork copied after it inherits the baseline. An *active* legacy Goal with a structurally valid open audit (a count of one or two) is also issued a fresh **Blocker identity** in the same transition: its description and count are preserved unchanged, the identity is not derived from the blocker text, and no extra unattended turns are granted. |
| **Token budget** | An optional cumulative bound on all Goal-owned token usage for one Goal identity, including attended and automatic work and each Budget wrap-up, with an extension-level default and maximum. Raising the bound preserves all usage history; it never resets or discounts prior usage. A raise is an absolute cumulative ceiling, must leave positive headroom over the accounted usage, and is at most the configured maximum. |
| **Budget wrap-up** | The single bounded, text-only summary of verified progress, remaining work, blockers, and the next useful action for one budget-exhaustion episode. It never marks the Goal complete or admits substantive tool work. Resuming with a higher Token budget cancels an undelivered wrap-up; a later exhaustion after that resume earns one new wrap-up. An in-flight wrap-up keeps its admitted usage, the old budget gate lifts only after the raise is durable, and no second old-budget wrap-up is sent. Editing the objective without resuming does not cancel an owed wrap-up; an undelivered wrap-up uses the latest durable objective. |
| **Active elapsed time** | Time accrued while a Goal is active in a live session, including idle-active time and excluding every non-active status and process downtime. |
