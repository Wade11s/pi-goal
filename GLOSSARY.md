# GLOSSARY

Domain vocabulary for pi-goal. Terms are used exactly as defined here in issue
titles, code, tests, and documentation; if a concept is missing, that is a gap to
close rather than a licence to invent a synonym.

| Term | Definition |
| --- | --- |
| **Goal** | A durable, session-scoped objective with a lifecycle status, a stable identity, and usage accounting. Persisted as custom session entries and reconstructed from the active session branch. One Goal per session at a time. |
| **Objective** | The user's finish line, stored verbatim and never rewritten by the extension. The one part of a Goal message the extension does not author, which is why it is always rendered as delimited, encoded data. |
| **Lifecycle status** | One of `active`, `paused`, `blocked`, `usage_limited`, `budget_limited`, `complete`. Only `active` continues automatically; every other status is a stop. Clearing is a durable tombstone, not a status. |
| **Continuation** | One further provider request pi-goal asks for at `agent_before_settle`, delivered as a `goal-continuation` custom message that restates the objective and asks for an evidence audit. Never scheduled by a timer and never driven from `agent_end`. |
| **Goal turn** | One run of Goal work: the run the user started (the kickoff) plus every run Pi started because pi-goal asked for a continuation. It is a *chain* of runs, because Pi can retry a failed provider request into a second run of the same Goal turn, and can compact for overflow recovery — a recoverable length stop or a context-overflow error — and retry the same response into another. The unit the blocked audit counts, and the unit the anti-loop counters count — although those only count *automatic* Goal turns, because a kickoff or a user-started run is attended. Evaluated at the settlement boundary, the only point where a Goal turn is known to be over. |
| **Activity** | Anything in a Goal turn that could move the objective: a tool call, non-whitespace output, or non-empty reasoning. Its absence is what an activity-free turn means. |
| **Completion audit** | The requirement-by-requirement, current-state-evidence check the model performs before calling `update_goal` with `complete`. Model-executed and extension-enforced only at the lifecycle level. |
| **Blocked audit** | The rule that the same genuine blocker must persist for at least three consecutive Goal turns before a Goal may become `blocked`. Enforced by the extension, not trusted to the model. |
| **Blocker** | The genuine condition preventing progress, as the model reports it through `update_goal`. Equivalent blockers (same condition, different wording) count as one; a genuinely different blocker restarts the audit. |
| **No-progress check** | The classification of the previous Goal turn as **progress**, a **verified wait**, or **no progress**. A verified wait polls a specific live handle; status narration and unexecuted plans are no progress. |
| **Conservative stop** | A deterministic, extension-owned stop that does not depend on the model's cooperation: repeated activity-free automatic Goal turns, or repeated execution-unavailable automatic Goal turns. Both move the Goal to `blocked`, which `/goal resume` ends with a fresh blocked audit. |
| **Activity-free turn** | An *automatic* Goal turn with no activity at all: no tool call, no output, no reasoning. Three in a row stop the Goal as `blocked`. A kickoff or a user-started run is attended work and never counts. |
| **Execution-unavailable turn** | An *automatic* Goal turn in which the model tried to run a command and the shell itself could not run it. An ordinary command failure — a non-zero exit code, a timeout, or an aborted command — is not one. Only a shell command that actually ran breaks the chain: a successful `get_goal` says nothing about the shell, and a shell call that never ran (invalid arguments, a permission block) is neither an execution failure nor evidence that the shell works, so it cannot hide a spawn failure. A Goal turn that ran no command at all also breaks the chain. Three in a row stop the Goal as `blocked`. |
| **Usage limit** | A provider failure whose evidence says the account, plan, or budget is exhausted. Read in two tiers: account or plan depletion (a provider usage-limit error code, a usage limit, a billing, plan, spending, account, or subscription limit in either word order, an account/plan/period quota or budget, an empty credit pool) is decisive and survives throttle wording in the same failure; a bare quota plus an exhaustion verb is not, because that is also how a per-minute quota metric is described. Moves the Goal to `usage_limited`, which `/goal resume` ends once the limit is resolved. A transient rate limit, an internal budget (`retry budget exhausted`), a negated statement, and a lookup — including a qualified one such as `account quota service reached a timeout`, because what decides is the *head* of the verb's object (its last word), not how the subject or a modifier was worded — are not one. Naming the API or the service as the *scope* of a limit (`You have reached your usage limit for the Anthropic API`, `Monthly usage limit reached for this service`, `You have reached the API usage limit`, `You have reached your service usage limit`) is still a usage limit: the verb reached a limit, not a lookup. The head cuts both ways, so `You have reached the quota service`, `You have reached the account quota service`, `You have reached the billing limit check`, and `You have reached the usage limit service` are lookups: the limit vocabulary in front of them is a modifier, and the object is the service or the check. The head noun is read rather than the raw end of the phrase, so a trailing comma, an exclamation mark, or a trailing adverb cannot hide it (`You have reached the quota service, please retry`, `You have reached the quota service now`), and the phrasal verb `reached out to` reaches what follows its particle. |
| **Terminal provider error** | A provider failure that is not a usage limit and that Pi is not retrying. It stops the continuation for that run and is surfaced, but it leaves the Goal active, so it is a per-run stop rather than a Conservative stop. |
| **User action** | A prompt the user types (including one queued while the agent is busy) or an abort. Ends the unattended phase and resets the anti-loop counters and the blocked audit. |
| **Replacement Goal** | A new Goal identity taking over a session's single Goal slot. Arrives with the lifecycle milestone; it resets every counter because the old ones describe work that no longer exists. |
| **Token budget** | An optional bound on unattended model usage, with an extension-level default and maximum. Reserved for the budget milestone. |
| **Active elapsed time** | Time accrued while a Goal is active in a live session, excluding paused durations and process downtime. Reserved for the budget milestone. |
